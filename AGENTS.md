# Repository Guidelines

## Project Structure & Module Organization
- `src/entrypoints/`: WXT entry points (content script `content.ts`, imports the CSS).
- `src/content/`: GitHub DOM observer, table injection, route parsing.
- `src/parser/`: CSV parsing, diff-table DOM extraction, per-UI selector config.
- `src/renderer/`: table rendering, row matching and inline cell diff utilities.
- `src/styles/`: extension UI styles (for injected diff tables).
- `example/`: sample CSV files for local verification (see PR #2).
- `wxt.config.ts`: WXT configuration (manifest + build); there is no hand-written `manifest.json`.
- `dist/`: build output generated by WXT (`chrome-mv3/`, `firefox-mv2/`); do not hand-edit.

## Build, Test, and Development Commands
- `pnpm dev` / `pnpm dev:firefox`: WXT dev mode with hot reload.
- `pnpm build` / `pnpm build:firefox`: production bundle in `dist/`.
- `pnpm lint` / `pnpm lint:fix`: Biome lint + format.
- `pnpm typecheck`: `tsc --noEmit` (also runs in CI).
- Load `dist/chrome-mv3/` in `chrome://extensions` (Developer mode, "Load unpacked"); Firefox loads `dist/firefox-mv2/` via `about:debugging`.
- Optional browser validation: `playwright-cli open --extension`.

## Coding Style & Naming Conventions
- Language: TypeScript with `strict` mode enabled.
- Formatting is enforced by Biome (`biome.json`): 2-space indentation, semicolons, double quotes, LF.
- Naming:
  - `camelCase` for variables/functions.
  - `PascalCase` for types/interfaces.
  - `kebab-case` for CSS class names (prefixed with `csv-diff-`).
- Keep modules focused (parser vs renderer vs content responsibilities).

## Testing Guidelines
- No automated test suite is configured yet (`package.json` has no `test` script).
- Validate changes by:
  - running `pnpm build`, `pnpm lint` and `pnpm typecheck` with no errors,
  - loading the unpacked extension,
  - checking CSV diffs on a GitHub PR diff page (PR #2 holds the sample CSVs).
- When adding tests later, place them near modules (for example `src/parser/*.test.ts`).

## Commit & Pull Request Guidelines
- Commits follow Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, ...), one concern per commit.
- PRs should include:
  - what changed and why,
  - before/after screenshots for UI changes,
  - manual verification steps (GitHub PR URL pattern and CSV sample used),
  - linked issue or context when available.
